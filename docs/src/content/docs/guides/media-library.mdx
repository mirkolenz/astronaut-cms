The admin panel includes a media library for uploading, renaming, replacing, and deleting media files.
It holds any kind of file, in folders nested as deeply as you like, on every backend.
Images and videos get thumbnails, and images, videos and audio files play in the preview.

## Configuration

Configure the media library in your `astro.config.ts`:

```ts title="astro.config.ts"
cms({
  media: {
    directory: "src/assets",
    maxFileSize: 100_000_000,
  },
});
```

### Options

| Option              | Type                               | Default        | Description                                                                                           |
| ------------------- | ---------------------------------- | -------------- | ----------------------------------------------------------------------------------------------------- |
| `directory`         | `string`                           | `"src/assets"` | Directory where media files are stored, relative to the project root                                  |
| `allowedExtensions` | `string[]`                         | any file       | Restricts the library to these extensions, e.g. `[".png", ".pdf"]`                                  |
| `maxFileSize`       | `number`                           | unlimited      | Maximum upload size in bytes, refused by the admin, and again by the server against the stored object |
| `optimizeImages`    | `ImageOptimizationConfig \| false` | enabled        | How an image is reshaped in the browser before it is uploaded                                         |

### File types

The library accepts any file unless `allowedExtensions` restricts it.
Hidden files (`.DS_Store`, `.gitkeep`) are never listed.
A file's content type comes from its extension, and one no registry can name is stored as a generic download.
HTML, SVG and other XML documents are always served with `Content-Disposition: attachment`, so an uploaded document cannot run as a page.

### Folders

Uploads land in the folder you have open, and **New folder** opens one that does not exist yet.
Neither a repository nor an object store keeps an empty directory, so a new folder exists once its first file is uploaded.
Renaming a file to `2026/summer/hero.png` moves it into that folder.

### Image optimization on upload

Images are reshaped in the browser before they are uploaded, so a 12 MP phone original never enters the library at full size.
By default an image is scaled to fit 2048x2048 and re-encoded if it exceeds 8 MB, keeping its own format.

```ts title="astro.config.ts"
cms({
  media: {
    optimizeImages: {
      maxWidth: 1600,
      maxHeight: 1600,
      format: "webp",
      quality: 0.85,
    },
  },
});
```

Only formats a browser can decode and encode are touched (JPEG, PNG, WebP, AVIF).
SVG, GIF, documents and any image already inside every limit are uploaded byte for byte.
Set `optimizeImages: false` to turn it off entirely, which is what you want when editors upload masters an object store is meant to hold.

<Aside type="note">
  This is not a replacement for astro's asset pipeline. The library keeps one sensible master, and
  the build still derives the per-breakpoint variants a page actually serves.
</Aside>

See [`ImageOptimizationConfig`](/astronaut-cms/reference/configuration/#imageoptimizationconfig) for every option.

## Where files are stored

By default the library is a directory in your repository (`media.backend: { type: "repo" }`).
Uploads are commits on the same draft branch as content, so an image and the entry that uses it publish together, and discarding a draft takes both back.

A library can also live in an object store, which is what you want when the media outgrows the repository: large or numerous files, editors uploading originals, or assets you would rather serve from a CDN than bundle into `dist/`.
Content then stores library keys instead of project paths, and the site loads them from `publicUrl`.

<Tabs>
  <TabItem label="S3-compatible">

    ```ts title="astro.config.ts"
    cms({
      media: {
        backend: {
          type: "s3",
          bucket: "my-media",
          endpoint: "https://s3.eu-central-1.amazonaws.com",
          region: "eu-central-1",
          publicUrl: "https://cdn.example.com",
        },
      },
    });
    ```

    Works with AWS S3, MinIO, Backblaze B2, Hetzner and anything else speaking the S3 API.
    Add `forcePathStyle: true` for a store that addresses objects as `<endpoint>/<bucket>/<key>`.
    Set `region` for a store whose endpoint does not name it and that rejects the `us-east-1` fallback.

  </TabItem>

  <TabItem label="Cloudflare R2">
    ```ts title="astro.config.ts"
    cms({
      media: {
        backend: {
          type: "r2",
          bucket: "my-media",
          accountId: "<cloudflare-account-id>",
          publicUrl: "https://cdn.example.com",
        },
      },
    });
    ```

    R2 speaks the S3 API, so this is the same backend with Cloudflare's endpoint filled in.

  </TabItem>
</Tabs>

### What an object store needs

<Steps>
  <StepItem title="Set the credentials on the server">
    On the server:

    ```sh
    ASTRONAUT_CMS_S3_ACCESS_KEY_ID=...
    ASTRONAUT_CMS_S3_SECRET_ACCESS_KEY=...
    # optional, for temporary credentials
    ASTRONAUT_CMS_S3_SESSION_TOKEN=...
    ```

    They are read by the CMS server alone and never reach the browser.

  </StepItem>

  <StepItem title="Decide how the library is read, and set publicUrl to match">
    Content stores plain keys, so a signed, expiring URL can never be written into an entry.
    `publicUrl` is the base those keys are served from. See
    [Reading the library](#reading-the-library) for the three ways to provide one, including
    keeping the bucket itself closed.

    Whatever serves it must **not** share an origin with the site — uploaded files would then be
    same-origin content in the admin. The integration refuses the configuration when your
    `astro.config` declares a `site` it can check against. See
    [Security Model](/astronaut-cms/guides/security/#serve-the-library-from-its-own-origin).

  </StepItem>

<StepItem title="Allow browser uploads in the bucket's CORS policy">
  A `PUT` from your admin's origin, with `content-type`, `if-none-match` and
  `content-disposition` among the allowed request headers: the server signs those terms into the
  upload URL, so the browser has to send them. Uploads go
  straight from the browser to the store, which is what keeps them clear of the 4.5 MB (Vercel) and
  6 MB (Netlify) function body limits.
</StepItem>

  <StepItem title="Set a lifecycle rule on the .trash/ prefix">
    The library keeps it for itself: deletions are moved there rather than dropped, and the media
    view restores them from it. The rule decides how long a deletion stays undoable, and is the only
    thing that eventually removes the bytes. See [Deleting and restoring](#deleting-and-restoring).
  </StepItem>
</Steps>

### Reading the library

Writing is always authenticated and always signed. Reading goes through `publicUrl`, which comes in two shapes.

#### A public bucket or CDN

The ordinary setup: `publicUrl` points at something anonymous readers can fetch.
On R2 that means a custom domain, since the `*.r2.dev` hostname is rate-limited and not meant for production traffic.

The admin then loads library files straight from that base.
It does not ask the CMS server where they are, because the key already is the URL, so a grid of thumbnails costs no function invocations at all.

#### A closed bucket behind a credentialed CDN (recommended)

You do not need the bucket itself to be public.
Put a CDN in front that holds the credential, deny everything else, and point `publicUrl` at the CDN:

- **AWS**: CloudFront with an [Origin Access Control](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-s3.html), and a bucket policy allowing only that distribution.
- **Cloudflare R2**: a [custom domain](https://developers.cloudflare.com/r2/buckets/public-buckets/#custom-domains) on the bucket. The bucket is not otherwise reachable.
- **Anything S3-compatible**: any CDN that can sign or authenticate to the origin.

As far as the CMS is concerned this is a public library, so nothing else changes and every optimization above still applies.
This is the setup to reach for when "the bucket must not be public" is the requirement.

### Deleting and restoring

An object store keeps no history, so deleting through the CMS moves the object to a `.trash/` prefix instead of dropping it.
The media view shows a **Trash** section listing what can still be brought back, with the path it would return to and when it was deleted.
**Restore** puts it back, refusing if something has taken the name since; **Delete permanently** is the one media action nothing undoes.

The trash is not a place you can otherwise address: it never appears in the library listing, no path can point into it, and it is reachable only through those two actions.

<Aside type="caution">
  A trashed object is still an object. On a public bucket it remains readable at its own URL until
  the lifecycle rule removes it, so "deleted" here means "recoverable", not "gone". When you need a
  file actually gone — someone asked you to remove their photo — delete it and then purge it from
  the trash.
</Aside>

The assistant can delete media but cannot restore or purge: those are the media view's alone.
That is deliberate, since the point of the trash is to catch a delete that should not have happened, including one the assistant made.

**A repository library has no trash and needs none.** Its deletions are a commit on the draft branch, so the file is still in Git: discard the changeset to bring it back before publishing, and it stays in history afterwards.

### Image optimization and adapter image services

| Setup                                       | How library images are optimized   |
| ------------------------------------------- | ---------------------------------- |
| Astro's built-in service, prerendered page  | Optimized at build into `dist/`    |
| Astro's built-in service, on-demand page    | Optimized per request by `/_image` |
| Vercel / Netlify / Cloudflare image service | Optimized at the edge              |

The adapter image services — `@astrojs/vercel` with `imageService: true`, `@astrojs/netlify`'s Image CDN, `@astrojs/cloudflare` with `imageService: "cloudflare"` — rewrite an `<Image>` into a CDN URL that carries your source URL as a parameter, and the CDN fetches that source **from its own edge at request time**.

The integration already registers `publicUrl` in astro's `image.remotePatterns`, which each adapter translates into its own allowlist (`vercel.json` image domains, netlify.toml `remote_images`), so there is nothing further to configure.

### How it differs from a repository library

- **Uploads and deletions are immediate.** There is no draft branch holding them, so publishing does not include them and discarding does not undo them. A deleted file stops being served to every visitor at once, even if the entry referencing it is still a draft.
- **Deletion is recoverable.** The object is moved to a `.trash/` prefix inside the library rather than dropped, and the media view restores it. See [Deleting and restoring](#deleting-and-restoring).
- **Uploads go browser-to-store.** The server signs a URL for that key, that byte count and that content type, and the store enforces all three as the write happens (see [Security Model](/astronaut-cms/guides/security/#uploads)). An occupied destination is refused by a signed precondition; replacing is the admin's explicit "Replace"/"Overwrite" action. The stored content type comes from the file extension rather than from the uploader, and active types (SVG) get `Content-Disposition: attachment` signed in as well, so the store serves them as downloads.
- **Content stores keys** (`photos/hero.png`) rather than project paths (`/src/assets/photos/hero.png`). Switching an existing site over therefore means moving the files into the bucket and dropping the directory prefix from the references your entries already hold; a leftover project path fails the build with a message naming it, rather than resolving to a URL that only looks right.
- **Astro's collection `image()` helper cannot hold a remote value.** Use the CMS's own `file()` for those fields, and resolve them with `astronaut-cms/Image.astro` or `resolveImage()`. See [Asset Handling](/astronaut-cms/guides/asset-handling/#object-store-libraries).
- **Nothing is bundled**, so `media.alwaysInclude` has no effect and images are optimized as remote images instead.

<Aside type="note">
  `astro dev` keeps the library in the working tree rather than the bucket, exactly as it
  substitutes local storage for content, so running the admin locally needs no bucket credentials
  and cannot touch what the deployed site serves. Only the bytes move: references are still written
  as keys, so an entry edited in dev builds unchanged. It needs local storage, since the files live
  in the working tree. Set `localMediaInDev: false` to point dev at the configured store instead —
  and note that a dev run has no sign-in at all, so anyone who can reach the dev server can reach
  the bucket.
</Aside>

## Using Media in Content

### In Content Collection Schemas

Use the `image()` helper from the schema function parameter to reference images in frontmatter:

```ts title="src/content.config.ts"
const blog = defineCollection({
  loader: glob({ pattern: "**/*.mdx", base: "src/content/blog" }),
  schema: ({ image }) =>
    z.object({
      cover: image().optional(),
    }),
});
```

Astro imports the file itself, so `entry.data.cover` is already `ImageMetadata` and goes straight
to `astro:assets` `<Image>`. Nothing has to be resolved at render time.

### In CMS Component Props

Write `props` as a function to receive the `image()` and `file()` helpers:

```ts title="src/cms.config.ts"
import { defineComponent } from "astronaut-cms/config";
import { z } from "zod";

defineComponent({
  props: ({ image, file }) =>
    z.object({
      photo: image(),
      attachment: file(),
    }),
});
```

A component prop is the one asset reference Astro has no mechanism for, so the CMS resolves it.
These props are stored as root-absolute path strings (e.g. `/src/assets/photo.png`) and turned into
optimized assets at render time. Render them with `astronaut-cms/Image.astro` or the
`resolveImage()`/`resolveFile()` helpers from `astronaut-cms/assets`, see
[Asset Handling](/astronaut-cms/guides/asset-handling/).

<Aside type="note">
  Each schema function is handed the helpers that work where it is: astro's `image()` in a
  collection schema, the CMS's `image()`/`file()` in a component's props. Nothing has to be
  imported, so no helper can be used in the file where it would not resolve. The one exception is
  `file()`, which *is* importable from `astronaut-cms/config` for a collection field, since astro's
  schema has no counterpart for it.
</Aside>

## Operations

The media library supports the following operations through the admin panel:

- **Upload** — Drag and drop or click to upload files to the media directory.
- **Rename** — Change the file name while preserving the extension.
- **Replace** — Upload a new file to replace an existing one at the same path.
- **Delete** — Remove a file from the media directory.

## Usage and unused files

**Check usage** reads your content once and then labels every file with how many entries use it, or
marks it unused. **Unused only** narrows the library to those, which is how an object-store library
is tidied up: uploads there are immediate, so a discarded draft leaves its uploads behind. The scan
is not run until you ask for it, since it reads every entry.

Deleting or renaming a referenced file warns first and names every entry that would break, so
neither can silently produce a broken build. The same check applies to the assistant, which refuses
both operations while a reference exists.

References are read from your content the way a build reads it — an `image()` or `file()` value is
an asset because its schema says so — plus a textual pass over bodies, so an image used only in
markdown prose or in a Markdoc tag still counts as referenced.

The same scan reports the opposite problem: **references pointing at files the library no longer
holds**. Only schema-declared references are reported there, since a path-shaped string in prose is
reason enough to keep a file but not to call an entry broken. With a repository library the build
catches these; with an object store nothing else does.

<Aside type="note">
  A file referenced only from site code is invisible to this scan, since the admin reads content and
  not your `.astro` files. List those under `media.alwaysInclude` (you already have to, for the
  build to bundle them) and they are excluded from the unused list too.
</Aside>
