Every asset reference is handled by whoever owns it. Astro resolves the ones it has a mechanism
for, and the CMS resolves only the one it does not: the props of your MDX components. Nothing is
injected into your Markdown or MDX at build time, so all of it works identically under Astro's
default `satteri()` pipeline and under `unified()`.

| Reference                            | Where                      | How it is handled                                                    |
| ------------------------------------ | -------------------------- | -------------------------------------------------------------------- |
| Markdown image `![alt](./x.png)`     | prose                      | Astro's Markdown processor, no extra wiring                          |
| `image()` schema field               | frontmatter, data          | Astro's content layer: `entry.data.cover` is already `ImageMetadata` |
| `image()` / `file()` component prop  | MDX component props        | Stored as a path string, resolved via `astronaut-cms/assets`         |
| Link to a file `[doc](/files/x.pdf)` | prose                      | Put the file in `public/` (plain URL)                                |

## Collection fields

Declare an image field with the `image()` helper Astro hands to a schema function. The admin panel
reads it as an image picker, and Astro imports the file for you, so the value you get back is
`ImageMetadata` and goes straight to `astro:assets`:

```ts title="src/content.config.ts"
const posts = defineCollection({
  loader: glob({ pattern: "**/*.{md,mdx}", base: "src/content/blog" }),
  schema: ({ image }) =>
    z.object({
      title: z.string(),
      cover: image(),
    }),
});
```

```astro title="src/pages/blog/[...slug].astro"
---
import { Image } from "astro:assets";
const { post } = Astro.props;
---

<Image src={post.data.cover} alt={post.data.title} width={1280} height={720} />
```

The media picker writes root-absolute paths (`/src/assets/hero.png`), which Astro resolves from
your project root; relative paths resolve against the entry file. Nothing in this path goes through
the CMS at render time.

<Aside type="note">
  Astro's schema helpers have no `file()`. For a non-image asset in a collection field, import
  `file()` from `astronaut-cms/config` and resolve it with `resolveFile()`, exactly as for a
  component prop below. `image()` is the other way round: it is never importable, because astro's
  is the one that works in a collection schema.
</Aside>

## MDX component props

A prop of a CMS component is the one reference Astro has no hook for, so the CMS resolves it. The
value is stored as a path string and turned into an optimized asset at render time:

```ts title="src/cms.config.ts"
Figure: defineComponent({
  props: ({ image }) => z.object({ src: image(), alt: z.string() }),
  source: "@/components/Figure.astro",
  defaultExport: true,
});
```

```astro title="src/components/Figure.astro"
---
import Image from "astronaut-cms/Image.astro";
import type { ComponentProps } from "@/cms.config";

type Props = ComponentProps["Figure"];
const { src, alt } = Astro.props;
---

<figure>
  <Image src={src} alt={alt} />
</figure>
```

`<Image>` accepts a path string or an `ImageMetadata`, so the same component works whether the
value comes from the CMS or from a manual import. For full control, call the resolvers directly:

```astro
---
import { resolveImage, resolveFile } from "astronaut-cms/assets";
const cover = await resolveImage("/src/assets/hero.png");   // -> ImageMetadata
const pdfUrl = await resolveFile("/src/assets/report.pdf"); // -> string URL
---
```

The `demo` workspace uses exactly this pattern for its `Figure` and `Hero` blocks, so it doubles as
an end-to-end example.

### Relative paths

Absolute paths are recommended, and the media picker writes them automatically. A relative path is
also accepted when you pass the content file it is relative to as `base`:

```astro
---
import { resolveImage } from "astronaut-cms/assets";

// "../../assets/photo.png" written in src/content/blog/post.mdx
const img = await resolveImage("../../assets/photo.png", "src/content/blog/post.mdx");
---
```

<Aside type="note">
  A relative path must resolve into your `media.directory`, since the map only covers that folder.
  Nothing hands an MDX component the path of the entry it was written in, so prefer absolute paths
  in props and keep `base` for the cases where you already have the entry in scope.
</Aside>

### React islands

The resolvers are async, which Astro awaits in `.astro` frontmatter. React components render
synchronously and cannot await, so resolve in an `.astro` wrapper and pass the already-resolved
`src` (or a plain URL) down to the island:

```astro title="src/components/Gallery.astro"
---
import Carousel from "@/components/Carousel.tsx";
import { resolveImage } from "astronaut-cms/assets";
const images = await Promise.all(Astro.props.srcs.map((s) => resolveImage(s)));
---

<Carousel client:visible images={images.map((i) => i.src)} />
```

## Assets live in the media directory

CMS asset props are resolved through a map rooted at your media directory, so a path outside it can
never resolve, however real the file is. The CMS enforces this when content is written, by hand or
by the assistant: an `image()`/`file()` value must name an existing file in the media library, and
any other path is rejected with the reason. A relative value is resolved against the entry holding
it first — the same way the build and `resolveImage(src, base)` resolve it — so it is judged by
where it points, not by how it is written. This is what keeps a mistyped or invented asset path
out of your content, where it would otherwise surface as a broken build.

Plain markdown links and `public/` URLs are unaffected, since they are ordinary strings and not
asset fields.

## Object-store libraries

Everything above describes a library that lives in your repository, where astro's asset pipeline
resolves and bundles the files. With `media.backend` set to an object store
([Media Library](/astronaut-cms/guides/media-library/#where-files-are-stored)) the same references
work, but they resolve differently, and it is worth knowing where the seams are.

Content stores a **library key** rather than a project path:

```json
{ "cover": "photos/hero.png" }
```

`resolveImage()` turns that key into a URL under the configured `publicUrl` instead of importing a
file, so it hands back a `string` rather than `ImageMetadata`:

```astro
---
import { resolveImage, resolveFile } from "astronaut-cms/assets";

const cover = await resolveImage("photos/hero.png"); // -> "https://cdn.example.com/photos/hero.png"
const pdf = await resolveFile("reports/q3.pdf");     // -> "https://cdn.example.com/reports/q3.pdf"
---
```

`astronaut-cms/Image.astro` handles both cases, so a component written for a repository library keeps
working unchanged:

```astro
---
import Image from "astronaut-cms/Image.astro";
---

<Image src={Astro.props.src} alt={Astro.props.alt} />
```

For a remote image it passes `inferSize` to `astro:assets`, which reads the real dimensions from the
image itself, at build time for a prerendered page. Pass an explicit `width` and `height` to skip that.
The integration adds your `publicUrl` to astro's `image.remotePatterns` for you (or, for a
[private library](/astronaut-cms/guides/media-library/#no-public-base-at-all), the store's own
origin, since that is where the build fetches from), which is what allows
astro to fetch and optimize those images at all.

<Aside type="caution">
  Astro's collection `image()` helper imports a local file, so it cannot hold a library key. For an
  asset field in a collection schema with an object-store library, use the CMS's own `file()` (or
  `image()` in a component's props) and resolve it as above. Everything else in this guide — MDX
  component props, `resolveFile()`, relative-path rules — is unchanged.
</Aside>

Nothing is bundled, because nothing is in the project to bundle: the build emits no copies, and
`media.alwaysInclude` has no effect. That also means a build cannot tell you an asset is missing.
The check moves earlier instead: the admin (and the assistant) refuse to write an `image()` or
`file()` value that is not in the library, which is the same rule, applied when the content is
written rather than when it is built.

## What a build bundles

A `dev` server resolves the whole media directory, so a file you have just uploaded works without a restart.
A production build is narrower: it bundles only the assets your content actually references, and leaves the rest of the library out of `dist/` entirely.

This matters because an unreferenced asset is not merely copied, it is copied _unoptimized_.
Astro only discards an original once it has produced a transformed version, which never happens for an image nothing renders.
A library that is mostly archive would otherwise ship at full size on every deploy.

The referenced set is worked out before the build, by reading your collections off disk. Every path
in it is one a schema declared to be an asset:

- Every `file()` value in frontmatter and in data collections, including inside arrays, records, tuples and discriminated unions.
- Every `image()` / `file()` prop of a CMS component in an MDX body, read against the prop schema in your `cms.config`, however deeply the value is nested in the prop.
- Relative paths, normalized against the entry that holds them, exactly as `resolveImage(src, base)` would.

Nothing is inferred from the shape of a string, so a prop that merely looks path-shaped
(`href="/src/assets/x.png"`) is left alone, and so is any quoted text in your prose.

Collection `image()` fields are not in that list, because Astro imports them into `entry.data`
itself and bundling them again would ship a second copy.
Markdown bodies are skipped for the same kind of reason: their relative images are Astro's own to resolve.
A Markdoc body is skipped because the CMS has no schema for its tags, so an asset a Markdoc tag names belongs in `media.alwaysInclude`.

Content the CMS or the AI assistant writes is committed before a build runs, so it is read like any other entry.
The same goes for a translation an i18n fallback renders in place of a missing one, since that is a real entry in another language directory.

<Aside type="caution">
  An `image()` or `file()` value the media directory does not hold fails the **build**, naming the
  entry and the field or prop it came from, rather than turning into a broken image at render time.
</Aside>

### Images keep only their optimized forms

Knowing _how_ content reaches an asset is worth as much as knowing _that_ it does.
An `image()` prop is going to `astro:assets`, which replaces the file with the transformed variants
each `<Image>` asked for, so the untouched original is never served and is not bundled.

A `file()` value is bundled as the file itself, since that is the whole point of `resolveFile()`.

If you want the original of an image the CMS only sees as an `image()`, for a "download the
full-size photo" link say, add it to `media.alwaysInclude`.
The build tells you so by name if you forget.

## Bundling a file nothing references

One kind of reference is invisible to the scan: a path written in your own code rather than in an entry.

```astro
---
// Nothing in src/content mentions this file, so the build does not know to keep it.
const og = await resolveImage("/src/assets/og-default.png");
---
```

List those under `media.alwaysInclude`, as globs relative to your media directory:

```ts title="astro.config.ts"
cms({
  media: {
    alwaysInclude: ["og-default.png", "brand/**"],
  },
});
```

The same applies to a path a body only assembles at render time, such as a template literal or any
other value the prop does not spell out as a literal.

Forgetting one is loud rather than silent: the build stops with `CMS image not found`, and the message points at `alwaysInclude`.

The media library itself is unaffected.
It lists files through the storage backend, not through the bundle, so every upload stays visible and pickable in the admin panel whether or not any entry references it yet.

## Downloadable files

For files you only link to (PDFs, archives), place them in `public/` and reference them by URL
(e.g. `/files/report.pdf`). They are served verbatim with no bundling step. Use a `file()` prop
with `resolveFile()` only when you want the file content-hashed and bundled.
