These functions and types are exported from `astronaut-cms/config`.

## `defineComponent()`

A type-safe wrapper for component definitions.
Returns the definition as-is, providing TypeScript inference.

```ts
function defineComponent<T extends z.ZodType>(def: ComponentDefinition<T>): ComponentDefinition<T>;
```

### Usage

```ts
import { defineComponent } from "astronaut-cms/config";
import { z } from "zod";

const Alert = defineComponent({
  props: z.object({
    type: z.enum(["info", "warning", "error"]),
  }),
  children: "markdown",
  label: "Alert",
});
```

## Schema helpers (`image`, `file`)

A component's `props` may be written as a function, which receives the asset helpers:

```ts
type SchemaHelpers = { image: () => z.ZodString; file: () => z.ZodString };

props: T | ((helpers: SchemaHelpers) => T);
```

`image()` and `file()` create Zod strings tagged with `x-cms-image` / `x-cms-file` metadata, which
the admin renders as pickers connected to the media library. The stored value is a root-absolute
path string; resolve it at render time with `astronaut-cms/Image.astro` or
`resolveImage()`/`resolveFile()` (see [Asset Handling](/astronaut-cms/guides/asset-handling/)).

### Usage

```ts
import { defineComponent } from "astronaut-cms/config";
import { z } from "zod";

const Hero = defineComponent({
  props: ({ image }) => z.object({ cover: image() }),
  children: "markdown",
});

const Download = defineComponent({
  props: ({ file }) => z.object({ document: file(), label: z.string() }),
});
```

`image` is deliberately not importable. A collection field takes astro's own `({ image })` and a
component prop takes the one its props function is handed, so there is no spelling that resolves in
one place and silently fails in the other.

## `file()`

The one asset helper that _is_ exported, because astro's collection schema has no counterpart for
it. Use it for a non-image asset in a `content.config.ts` field:

```ts title="src/content.config.ts"
import { file } from "astronaut-cms/config";

const pages = defineCollection({
  loader: glob({ pattern: "**/*.mdx", base: "src/content/pages" }),
  schema: ({ image }) =>
    z.object({
      cover: image(), // astro's helper: resolved into entry.data
      brief: file().optional(), // the CMS's: a path string, resolved with resolveFile()
    }),
});
```

Inside a `cms.config.ts` props function, take `file` from the helpers instead of importing it.

## `InferComponentProps`

A utility type that maps each component name to its inferred prop types.
Use this to type-check Astro component props against the CMS schema.

```ts
type InferComponentProps<Components extends Record<string, ComponentDefinition>> = {
  [Name in string & keyof Components]: Components[Name] extends ComponentDefinition<infer T>
    ? z.infer<T>
    : never;
};
```

The props schema is inferred the same way from either form, so a component that declares its props
directly and one that takes the helpers are indistinguishable to consumers.

### Usage

Export a bound `ComponentProps` type from your CMS config file:

```ts title="src/cms.config.ts" {1} {5}
import { defineComponent, type InferComponentProps } from "astronaut-cms/config";
import { z } from "zod";

export const components = {/* ... */};
export type ComponentProps = InferComponentProps<typeof components>;
```

Then use indexed access in your Astro components:

```astro title="src/components/Alert.astro"
---
import type { ComponentProps } from "@/cms.config";

type Props = ComponentProps["Alert"];

const { type } = Astro.props;
---

<div class={`alert alert-${type}`}>
  <slot />
</div>
```

## `ComponentDefinition`

The interface for a single component definition.

```ts
interface ComponentDefinition<T extends z.ZodType = z.ZodType> {
  props: T;
  children?: "markdown" | Record<string, ComponentDefinition>;
  kind?: "flow" | "text";
  source?: string;
  defaultExport?: boolean;
  label?: string;
  icon?: LucideIcon;
  editor?: ComponentType<JsxEditorProps>;
}
```
