These functions and types are exported from `astronaut-cms/config`.

## `defineCollection()`

Types one entry of the `collections` export of `cms.config.ts`, keyed by collection name like `content.config.ts`.

```ts
function defineCollection(options: CollectionOptions): CollectionOptions;

interface CollectionOptions {
  sort?: "id" | "natural" | "file"; // default: "id"
}
```

## `defineComponent()`

A type-safe wrapper for component definitions.
Returns the definition as-is, providing TypeScript inference.

```ts
function defineComponent<T extends z.ZodType>(def: ComponentDefinition<T>): ComponentDefinition<T>;
```

### Usage

```ts
import { defineComponent } from "astronaut-cms/config";
import { z } from "zod";

const Alert = defineComponent({
  props: z.object({
    type: z.enum(["info", "warning", "error"]),
  }),
  children: "markdown",
  label: "Alert",
});
```

## Schema helpers (`image`, `file`, `link`, `reference`)

A component's `props` may be written as a function, which receives the asset, link and reference helpers:

```ts
type SchemaHelpers = {
  image: () => z.ZodString;
  file: () => z.ZodString;
  link: () => z.ZodString;
  reference: (collection: string) => z.ZodString;
};

props: T | ((helpers: SchemaHelpers) => T);
```

`image()` and `file()` create Zod strings tagged with `x-cms-image` / `x-cms-file` metadata, which
the admin renders as pickers connected to the media library. The stored value is a root-absolute
path string; resolve it at render time with `astronaut-cms/Image.astro` or
`resolveImage()`/`resolveFile()` (see [Asset Handling](/astronaut-cms/guides/asset-handling/)).

### Usage

```ts
import { defineComponent } from "astronaut-cms/config";
import { z } from "zod";

const Hero = defineComponent({
  props: ({ image }) => z.object({ cover: image() }),
  children: "markdown",
});

const Download = defineComponent({
  props: ({ file }) => z.object({ document: file(), label: z.string() }),
});
```

`link()` creates a Zod string tagged with `x-cms-link` metadata.
It accepts relative, `http`, `https`, `mailto` and `tel` URLs, and it is the only way to store a URL.
Every other string field, `z.url()` aside, refuses a value that would act as a link, such as `https://example.com`, `//host`, `mailto:a@b.c` or `javascript:alert(1)`.
`z.url()` works too, but it only takes absolute URLs, and the CMS limits it to the same schemes.

```ts
const CallToAction = defineComponent({
  props: ({ link }) => z.object({ label: z.string(), href: link() }),
});
```

`reference(collection)` stores the id of an entry in another collection, which the admin offers as a picker and checks on save.
The component receives the id and can look the entry up with `getEntry()`.

```ts
const TeamMember = defineComponent({
  props: ({ reference }) => z.object({ member: reference("team") }),
});
```

`cms.config.ts` is bundled into the browser admin, so it cannot import `content.config.ts` or anything from `astro:content`.
Keep values both configs use, such as a shared `z.enum()` of colours, in a module of their own that each imports.

`image` is deliberately not importable. A collection field takes astro's own `({ image })` and a
component prop takes the one its props function is handed, so there is no spelling that resolves in
one place and silently fails in the other.

## `file()` and `link()`

The helpers that _are_ exported, because astro's collection schema has no counterpart for them.
Use them for a non-image asset or a URL in a `content.config.ts` field:

```ts title="src/content.config.ts"
import { file, link } from "astronaut-cms/config";

const pages = defineCollection({
  loader: glob({ pattern: "**/*.mdx", base: "src/content/pages" }),
  schema: ({ image }) =>
    z.object({
      cover: image(), // astro's helper: resolved into entry.data
      brief: file().optional(), // the CMS's: a path string, resolved with resolveFile()
      website: link().optional(), // the only kind of field that may hold a URL
    }),
});
```

Inside a `cms.config.ts` props function, take `file` and `link` from the helpers instead of importing them.

## `InferComponentProps`

A utility type that maps each component name, nested children included, to its prop types.
Use this to type-check Astro component props against the CMS schema.

The types are the schema's input, since MDX passes attributes exactly as written.
A prop with `.default()` is therefore optional, and the component applies the default itself.
Children declared in a parent's `children` map are part of the result, as long as the parent is written with `defineComponent()`.

The props schema is inferred the same way from either form, so a component that declares its props
directly and one that takes the helpers are indistinguishable to consumers.

### Usage

Export a bound `ComponentProps` type from your CMS config file:

```ts title="src/cms.config.ts" {1} {5}
import { defineComponent, type InferComponentProps } from "astronaut-cms/config";
import { z } from "zod";

export const components = {/* ... */};
export type ComponentProps = InferComponentProps<typeof components>;
```

Then use indexed access in your Astro components:

```astro title="src/components/Alert.astro"
---
import type { ComponentProps } from "@/cms.config";

type Props = ComponentProps["Alert"];

const { type } = Astro.props;
---

<div class={`alert alert-${type}`}>
  <slot />
</div>
```

## `ComponentDefinition`

The interface for a single component definition.

```ts
interface ComponentDefinition<T extends z.ZodType = z.ZodType> {
  props: T;
  children?: "markdown" | Record<string, ComponentDefinition>;
  kind?: "flow" | "text";
  source?: string;
  defaultExport?: boolean;
  label?: string;
  icon?: ComponentIcon;
  editor?: JsxEditor;
}
```
